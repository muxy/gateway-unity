# Live-Editor compatibility and PIN validation

**Historical procedure for SDK commit `e1c80fb`:** its private-field cleanup matches the original transport. For current SDK testing use [the shipping transport procedure](../Validation~/Shipping-Transport.md), which exercises public connection/disposal APIs and needs no replacement socket.

This is a fallback for a licensed, already-running Unity Editor when a separate batch process fails activation. It is validation tooling for the current SDK internals, not a runtime integration example or a replacement for clean-project/package/player tests.

1. Use a disposable or checkpointed test project. Record its exact Editor version, existing dependencies, and baseline errors. Back up `Packages/manifest.json` and `packages-lock.json` before adding test dependencies.
2. Install the local SDK package under `com.muxy.gateway`. The Editor probe also needs `com.unity.modules.jsonserialize: 1.0.0`; record whether that was already present. This module belongs to the probe, not to the SDK's runtime requirements.
3. Create a unique output directory outside the SDK package. In the test project, create `Temp/GatewayLiveValidation/settings.json`:

   ```json
   {
     "outputDirectory": "D:/GatewayValidation/unique-run",
     "gameId": "gamelink-testing"
   }
   ```

4. Copy `GatewayLiveValidation.cs` into a dedicated `Assets/GatewayLiveValidation/Editor` directory. Refresh assets or refocus the Editor and wait for compilation. The probe writes `compatibility-result.json` and then `state.json` with `waiting-for-pin`. An existing `authentication-result.json` prevents a repeat authentication session; use a new output directory for another run.
5. Obtain a new production configuration PIN from the matching Gateway Twitch extension. Immediately write a request to `Temp/GatewayLiveValidation/pin-request.json`, using that PIN and the UTC time at which it was requested:

   ```json
   {
     "pin": "<fresh six-character PIN>",
     "generatedAtUtc": "<UTC ISO-8601 request timestamp>"
   }
   ```

6. The probe consumes/removes the request, opens a new native-derived production WSS route with ordinary certificate validation, calls the real SDK PIN API, pumps native payload/response handling on the main thread, and tests the returned refresh token only in memory. Wait for `authentication-result.json`. A pass requires callbacks, native authenticated state, JWT/refresh-token presence, and cleanup. No token strings or raw server payloads are written to results or forwarded through native debug logs.
7. For the custom-consumer check, use the `Gateway.PackageConsumer.asmdef` and `GatewayPackageConsumer.cs` fixture generated by `Test-PackageImport.ps1` under `Assets/GatewayLiveValidation/Consumer`. Copy `GatewayLiveConsumerValidation.cs` beside the Editor probe. It verifies the separate consumer assembly and six public types, then writes `consumer-result.json`. It can run after authentication without authenticating again.
8. Save sanitized results, the tested source/native/probe hashes, and the resolved dependency versions. Keep failed attempts with their actual scope. A missing callback is not proof of an expired PIN, and a compilation/helper error is not a backend rejection.
9. After native cleanup finishes, remove only the owned temporary probe assets/control files and reverse the test package changes. Restore exact backups when nothing else changed; otherwise remove only the test entries and preserve other project changes. Leave the user's Editor/project open.

The validation transport is intentionally separate from the SDK's shipped transport. The SDK stage helpers still need secure/awaitable defaults and lifecycle fixes. The probe currently inspects private SDK fields, detaches only its own idle transport's event delegates, and releases its native instance explicitly. Revisit those test internals when SDK disposal is implemented. These checks do not prove the public SDK has deterministic disposal, that all callback handles are bounded, or that server tokens were revoked.
